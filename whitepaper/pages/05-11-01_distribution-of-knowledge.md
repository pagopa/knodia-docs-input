To implement the functionality described in this proposal, *Interop Nodes* need to communicate. Two modes of communication are envisioned:

1. queries and commands that an *Interop Node* sends to another synchronously while processing a request from an *Operator* or, in general, to carry out the described flows;
2. propagation of events for state changes of entities (Organizations and *Federated Attributes* associated to them, *E-Services*, *Agreement Requests*, *Purpose Statements*, etc.) from the *Interop Node* where the change occurs to other interested *Interop Nodes*.

Note that, in both cases, the data exchanged between *Interop Nodes* does not contain personal data of natural persons.

The first mode of communication occurs, for example, when searching for *E-Services* offered in another *Interop Node* or when creating an *Agreement Request*. These communications can be classified as either queries (read operations that do not change the state of the *Interop Nodes*) and commands (by which, e.g., an *Interop Node* requests another to create an entity, like an *Agreement Request* or *Purpose Statement*).

The second mode is used to forward relevant events between *Interop Nodes* to ensure their state is consistent with each other. These events include, for example, when a *Federated Attribute* of an Organization is revoked or when an *Agreement Request* is suspended by the *E-Service* *Producer*. The event is generated by an *Interop Node*, but it is useful to propagate it to other *Interop Nodes* so they can update the state of other entities and/or notify the Organizations concerned.

# Means of communication

Both modes of communication are implemented as HTTP APIs, using JSON for request and response bodies. This API was heretofore referred to as *Federated API*. Every *Interop Node* must implement the endpoints of this API following an OpenAPI specification to be defined by the *Federation Consortium*, capitalizing on the effects of the proposed experimentation.

Synchronous queries and commands will therefore be implemented as HTTP requests (with methods GET, POST, or other as appropriate) from an *Interop Node* to another.

For event propagation, every *Interop Node* must provide endpoints that allow other *Interop Nodes* to retrieve events generated by that *Interop Node*. Propagation is therefore by *pull*: the *Interop Node* that is interested in the events must send the request via polling.

We consider the pull strategy preferable to a push one (e.g., using webhooks) so the *Interop Node* does not have to manage fan-out (e.g., for each event, call the webhooks of all other *Interop Nodes*) and retries in case the target *Interop Node* is temporarily unreachable (which is an occurrence the source *Interop Node* cannot control). A pull strategy makes the source node responsible only for reliably providing its endpoints.

The proposed approach based on polling could be replaced by an *Interop Node* exposing a message broker to which other *Interop Nodes* can connect as consumers. This option could be more efficient in terms of latency and throughput. However, mandating every *Interop Node* to include a message broker imposes stronger technical constraints on implementers. If a single message broker is standardized throughout the *Cross-Border Federation* (e.g., Kafka), every *Interop Node* implementer is forced to adopt it. If several are supported (e.g., an *Interop Node* could use Kafka and another an AMQP-compliant broker), implementers must support several protocols to consume events from multiple *Interop Nodes*. A pull-based HTTP API leaves implementers greater technological autonomy while keeping a standard interface. *Interop Nodes* can still, at their discretion, use message brokers or queues internally.

To guarantee event retrieval is efficient, the dedicated endpoints must include filters to select the events to retrieve. For instance, each *Interop Node* is interested only in retrieving events related to *Agreement Requests* related to their Organizations and to entities related to that *Agreement Request*.
